# 《每周一龙》写作风格指南

{/* SPDX-License-Identifier: CC-BY-NC-SA-4.0 */}

本文档基于对全部 54 期《每周一龙》约 1,836 条报道项目的定量与定性分析，
总结归纳了本栏目的写作风格规范。风格会随时间演化，本文档反映的是截至
2025 年初的整体面貌。

:::info[目标读者]

本文档的读者包括《每周一龙》的**人类编辑**与**AI 智能体协作者**（笔者使用的编码助手）。
目的有二：

- 帮助人类编辑保持风格一致性；
- 告诉 AI 智能体在代写初稿时应遵循何种模式。

:::

## 计量分析脚本

本风格指南基于 [`scripts/analyze-newsletter.py`](../../scripts/analyze-newsletter.py)
的计量结果编写。该脚本解析全部周报，输出每条项目的字数、句数、动词挂链比例、
编辑语气检测、科普深度等指标。复现命令见脚本顶部的文档字符串。

## 简明性

### 每条项目的长度

| 统计量 | 数值 |
|---|---|
| 平均字数 | 51 字 |
| 中位字数 | ~35 字 |
| 平均句数 | 1.5 句 |
| 正好 1 句的项目 | 66.1% |
| 1–2 句的项目 | 87.6% |

绝大多数项目只有 **一到两句话**。如果一个项目超过了 3 句话，应当考虑拆分
（前提是不影响可读性）或确认其确实构成一个不可分割的报道单元。

### 规范

- 常规报道项目控制在 **1–2 句**，**20–80 字**。
- 若有补充说明（解释背景、原因、影响），可追加 1–2 句，但总量不宜超过 5 句。
- 项目符号项目通常更短（30–40 字），适合列表式浏览。
- 每期平均 25–50 条项目；合订本可达 60–190 条。

## 句子构造

### 主导模板

报道类项目几乎全部遵循以下模板：

> **动作发出者** `[`**动作动词**+了`](`链接`)` **对象/补充说明**

示例：

```
Huacai Chen [发出了](https://lore.kernel.org/...) 适用于龙芯 3 号处理器的自动调频驱动。
Xi Ruoyao [修复了](https://gcc.gnu.org/...) LoongArch 硬件断点的几个实现问题。
Bibo Mao [实现了](https://lore.kernel.org/...) KVM 半虚拟化快速自旋锁。
```

### 链接的位置

- **55.3% 的链接直接挂在动词上**——这是最标志性的风格特征。
- 其余链接放在名词短语上（`[上游的跟踪 issue](url)`、`[相关内核补丁](url)`）。
- 新项目应当优先采用动词挂链模式。

### 高频动词（挂链接）

以下是在已发布内容中链接直接挂在动词上的前 10 个高频动词：

`修复了`(96)、`增加了`(47)、`贴出了`(29)、`提交了`(24)、`优化了`(19)、
`发布了`(18)、`实现了`(18)、`发出了`(14)、`合并了`(12)、`允许了`(12)

### 时态

- **过去完成时**（动词 + 了）是报道项目的主导时态。这是新闻写作的自然选择。
- **现在时/进行时**用于解释性内容：`这意味着…`、`鉴于此…`、`目前…`。
- 项目符号项目有时省略句号，但仍保留动词完成时标记 `了`。

## 编辑评论

### 何时注入评论

约 10% 的项目包含明确的编辑声音（不含独立的 `:::info` 块）。
编辑评论在以下场景出现：

| 场景 | 典型用语 |
|---|---|
| 感谢贡献者 | `辛苦了！`、`欢迎欢迎！`、`让我们感谢…`、`（感谢 … 的线索投递）` |
| 更正/道歉 | `更正声明`、`有失偏颇`、`在此谨向…道歉` |
| 解释事物意义 | `这意味着…`、`鉴于此…`、`因此…` |
| 提供历史背景 | `从前…`、`先前…`、`在…的年代` |
| 推测/分析 | `大概率…`、`笔者猜测…`、`笔者认为…` |
| 代码质量评议 | `不可接受`、`遑论`、`优雅不能当饭吃` |
| 主编点评 | 对 ABI 决策、工具链变更等重大事项的专门评述 |

### `:::info` 块的使用场景

- **技术深度剖析**：解释某机制如何运作（如链接器松弛的原理）
- **历史背景**：提供事件的前因后果（如某 PR 为何推迟）
- **更正/澄清**：对之前报道内容进行补充或修正
- **主编点评**：对重大设计决策发表看法
- **引用声明**：如版权合理使用声明
- `:::tip` 块用于轻松的花絮或小知识

### 规范

- 编辑语气应**自然、有节制**。不要每一条都评论。
- `:::info` 块应有明确标题（`[标题]`），内容自成一格。
- 纠正先前报道时，使用 `:::info[更正声明]` 格式，措辞正式、负责。
- 致谢应真诚而简洁；避免浮夸。

## 科普

### 当前科普深度分布

基于对 1,836 条项目的自动化分类：

| 科普深度 | 数量 | 比例 |
|---|---|---|
| 无科普（纯报道） | 1,226 | 66.8% |
| 浅度科普（1 个解释线索） | 337 | 18.3% |
| 中度科普（2–3 个解释线索） | 201 | 10.9% |
| 深度科普（4+ 个解释线索） | 72 | 3.9% |

科普率呈上升趋势：2023 年 28.0% → 2024 年 38.7% → 2025 年（早期数据）40.3%。

### 什么内容需要科普

以下是**获得深度科普**的典型话题领域：

| 话题 | 说明 |
|---|---|
| **Linux 内核内部机制** | 为什么 LoongArch 用 `statx` 而不是 `fstat`、vDSO `getrandom` 的安全属性、半虚拟化如何实现 566% 的性能提升 |
| **ABI 设计决策** | 为什么 `R_LARCH_CALL36` 保持其编码、「PC-relative」与「PC-aligned」语义的差异、为什么从未添加 `pcaddu18i` |
| **编译器优化原理** | 为什么 `bstrins` 优于移位+掩码、链接器松弛与 `-mexplicit-relocs` 的交互、GCC CoreMark 回归的四个独立根因 |
| **ISA 设计** | FP16/FP128 编码空洞的指令位域分析、LA464 的 32 位除法未定义行为、LA664 如何修复 |
| **工具链背景知识** | BOLT 是什么、文档库状态为何阻碍 binutils 变更 |

以下内容通常**不需要科普**，纯报道即可：

- 常规缺陷修复（`修复了…` 后不跟 `因为…`）
- 简单功能添加
- 发行版新闻（`X 发布了 ISO`）
- 大多数 LLVM 单条补丁
- 社区整活儿/游戏测试

### 科普的推荐结构

当需要科普时，建议遵循「三段式」：

1. **事实**（1 句，过去时）：X \[做了\](链接) Y。
2. **为什么重要 / 如何运作**（1–3 句，现在时）：这是需要的，因为 Z。这意味着…
3. **影响 / 建议**（0–1 句）：因此，用户应该… / 这将启用…

### 科普的量化标准

自动化脚本使用以下七类解释性话语标记词来估计科普深度：

| 类别 | 标记词示例 |
|---|---|
| **原因** | 因为、由于、这是因为、原因是、具体来说 |
| **后果** | 这意味着、这会导致、其作用、其目的是 |
| **目的** | 用于、以实现、来达到、从而、以便 |
| **对比** | 相比之下、与…不同、而非、而不是 |
| **时间** | 先前、此前、过去、原本、现在、随后 |
| **定义** | 是一种、指的是、对应、等同于、相当于 |
| **情态** | 需要、要求、必须、应该、可以 |

计数 ≥ 4 → 深度科普；2–3 → 中度；1 → 浅度；0 → 纯报道。

## 举例

### 纯报道（无科普）

```
Tiezhu Yang [修复了](https://lore.kernel.org/...) 用户态断点对线程标志
TIF_LOAD_WATCH 处理的一些细节。
```

### 轻度科普

```
Hui Li [修复了](https://lore.kernel.org/...) LoongArch 硬件断点的几个实现问题。
```

### 中度科普

```
7 月 5 日，Sui Jingfeng [合并了](https://cgit.freedesktop.org/...) 龙芯显示控制器 DRM 驱动。
他在前一天[拿到了](https://gitlab.freedesktop.org/...) drm-misc 仓库的合并权限。
这意味着集显用户应该能用未来的上游内核亮屏了；2D/3D 渲染加速是另外的工作。
```

### 深度科普 + 编辑评论

参见历期 `:::info` 块中关于链接器松弛、ABI 设计决策、ISA 指令编码分析等长篇论述。
这类内容通常位于独立的注释块中，而非内嵌于报道条目。

## 报道准则

### 来源链接

**TWiL 的每条报道项目必须带有至少一条来源链接。** 这是为了读者可以自行验证、
深入了解报道内容，也便于后续追溯。纯编辑项目（如过渡语、栏目介绍等样板内容）不在此限。

此规则适用于所有栏目，包括 `社区整活:儿:`。如果内容没有公开链接可引用，则说明
编辑无从得知此事——如果真的存在确实值得报道、但仅见于非公开渠道（如微信聊天记录，
微信不支持导出群聊记录为公开链接）的内容：

- 编辑**必须**先向原作者征得转载许可。
- 获得许可后，编辑应以截图或其他适合引用的形式将内容搬至公开可见的地址，并在周报中引用该地址。
- 编辑**不得**代为猜测或编造 URL。如无法提供来源链接，该条应被删除。

:::info[对 AI 智能体的附加要求]

AI 智能体在处理无链接的报道项目时：

- 如果可自行查找到公开来源（如 lore.kernel.org、GitHub PR），必须明确告知用户
  自己查到了链接，并**请用户二次确认**，以防幻觉。
- 如果无法查找到来源，必须向用户报告并请求提供链接；不得绕过此步骤直接发布。
- 在提交说明中记录链接来源的获取方式（自行查找并提供链接 / 用户提供 / 无法获取已删除）。

:::

### 补丁集报道粒度

补丁集（patchset）是 Linux 内核与工具链新闻的主要素材来源。为保持扫读性：

- **只报道最新版本中有实质性变化的修订。** 「实质性变化」指：设计方案大改、在相似设计下重写实现、
  或从他处接管了上游工作（作者变更）。
- 常规的审阅跟进、小幅修正（如拼写修正、补充注释、cc stable 的添加与移除等）**不构成报道条目**。
- 如果某补丁集在前几期已被报道过，且本周的新版本无实质性变化：**删除该条目**。
- 换言之，只有**非平凡的工作提交通知**和**正式发布（合入主线、tag 新版本等）**才算作「新闻」。
  常规跟进工作不算。

此规则意味着大多数来自其他通讯的「v1→审阅→v2→审阅→v3」链条在被适配后将缩减为
**至多一句话**（如果最新版本有实质性变化），或者**整个条目被移除**（如果只是第 N 次小修小补）。

## 适配来自其他通讯的投稿

有时贡献者（包括新编辑）可能同时为其他 LoongArch 通讯供稿。这些通讯的读者群体不同，
导致原始稿件的风格可能与 TWiL 存在系统性差异：

- **面向非技术读者**的通讯会包含大量括号内的术语解释、逐轮审查追踪；
- **TWiL 面向技术读者**，期望读者能够自行查阅链接或背景知识，且每条项目独立、可扫读。

### 典型差异与处理方式

| 差异 | 其他通讯的风格 | TWiL 的处理方式 |
|---|---|---|
| **审查周期** | 追踪 v1→审阅→v2→审阅→v3 的完整过程 | 适用[补丁集报道粒度](#补丁集报道粒度)：仅保留有实质性变化的最新版本；无实质性变化则整条删除 |
| **术语解释** | `PR_SET_SYSCALL_USER_DISPATCH（是一个 Linux prctl 操作，用于…）` | 删除括号解释。如果某个概念确实需要为 TWiL 读者科普，放入 `:::info` 块 |
| **项目覆盖** | 详尽的列表（如 Box64 的全部 11 条 PR） | 挑选 2–3 个最重要的亮点；其余可省略或用一句话概括 |
| **动词选择** | `添加了` | 替换为 `增加了`（TWiL 偏好更抽象的动词） |
| **编辑声音** | 中性、冷调、无评论 | 如果有值得评论的内容，可补充 `:::info` 或简短的「这意味着…」；若无则不强加 |

### 适配清单

收到面向其他通讯撰写（或受其风格影响）的原始稿件时，按以下步骤处理：

1. **应用补丁集粒度规则**：将包含多个补丁版本或审查轮次的项目拆分或删除。
   只保留有[实质性变化](#补丁集报道粒度)的最新版本（设计大改、实现重写、作者变更等）；
   常规跟进工作（拼写修正、cc stable 增删、审阅往返）整条删除。
2. **检查来源链接**：确保每条报道项目至少有 1 条来源链接。
   对无链接的条目：自行查找链接并请用户二次确认，或向用户请求提供。无法提供链接的条目删除。
   遵守[来源链接](#来源链接)的全部约束（包括 `社区整活:儿:` 栏目的公开可溯源要求）。
3. **删除内联科普**：移除报道句中的括号解释（`（是…，用于…）`）。
   如某概念确实需要为 TWiL 受众解释，将其扩展为独立的 `:::info` 块。
4. **裁减详尽的列表**：将过长的条目列表（如某个项目的每笔提交都单独列出）精简为 2–3 个重点。
5. **统一措辞**：检查并替换偏离风格指南的关键词汇（如 `添加` → `增加`）。
6. **检查栏目完整性**：确认所有必备栏目（`先「马」再看`、`杂闻播报`、`张贴栏`）均已覆盖。
   `社区整活:儿:` 栏目非强制：如果本周没有足够有趣的社区内容，可省略。
7. **补充编辑评论**（按需）：如果本期有值得深度探讨的技术话题，添加 1–2 个 `:::info` 块；
   如果自然出现了值得感谢的贡献者或值得评论的代码质量话题，使用既有的编辑语气标记。
   不强求——宁可保持一期偏报道风格，也不生硬套用编辑个性。
8. **修复元数据**：确认 `slug`、`date`、`draft` 状态等 frontmatter 字段正确无误。
